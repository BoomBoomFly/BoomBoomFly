# BoomBoomFly 参考框架采用与演进路线

本文记录外部参考项目在 BoomBoomFly 中的采用边界，以及当前自有框架从骨架走向任务闭环的实施顺序。
长期仓库职责和安全不变量仍以[工作区架构](工作区架构.md)为准，当前完成度和停止条件见
[当前交接](handoff.md)。

## 1. 总体结论

BoomBoomFly 不以集成一个大而全的第三方自治框架为目标。自有框架由稳定的能力接口、单一飞行执行器、
可替换的导航算法和任务应用组成：

```text
地面站 / 小车通信
             │
感知 ────────┼──> H 任务 / D 任务
             │       任务策略：当前为 FSM，未来可选行为树
设备  <──────┘              │
                             v
                  boomboom_navigation
             网格 / 航点 / 跟踪 / 降落引导
                    │             │
                基础实现      可选规划后端
                              GCOPTER / EGO
                    │
                    v
             ExecuteFlight Action
                    │
                    v
              offboard_cpp 飞行网关
              唯一 PX4 控制写入方
                    │
                    v
                   PX4

视觉里程计 / TF ──> px4_vision_bridge ──> PX4 EKF2
```

框架的核心不是统一基类或插件系统，而是以下稳定边界：

- `common` 唯一定义跨仓库公共信息模型和 ROS-free C99 core。
- `offboard_cpp` 独占 PX4 Offboard 控制输入并实现所有飞行安全语义。
- `boomboom_navigation` 把任务意图转换为飞行能力请求或轨迹，不取得 PX4 写权限。
- `boomboom_mission_core` 管理任务生命周期；每个 `boomboom_task_*` 只定义本任务策略。
- `px4_bringup`、manifests 和验证脚本管理部署与可复现性，不承载业务状态机。

## 2. 参考项目采用边界

| 参考项目 | 借鉴内容 | 当前决策 |
|---|---|---|
| [PX4 ROS 2 Interface Library](https://github.com/Auterion/px4-ros2-interface-lib) | `Mode`、`ModeExecutor`、模式所有权、RC/GCS 接管和 PX4 failsafe 集成。 | 不加入核心 manifest，不替换当前 direct-Offboard gateway。当前 gateway 形成独立 SITL 基线后，才可在隔离分支以与 PX4 v1.16.2 匹配的 `release/1.16` 精确提交做 A/B。 |
| [Aerostack2](https://github.com/aerostack2/aerostack2) | 能力 Action、平台适配、仿真/实机同接口、每机 namespace 和可替换后端。 | 只借鉴架构思想，不引入完整框架；其职责与现有 gateway、navigation、bringup 和任务层大量重叠。 |
| [BehaviorTree.CPP](https://github.com/BehaviorTree/BehaviorTree.CPP) | 异步 Action、并行、重试、Fallback 和运行时任务树。 | 第一阶段不用。只有任务并行、重试和条件分支显著增长后，才允许替换某个任务的策略 FSM；不得进入飞行安全执行层。 |
| [BehaviorTree.ROS2](https://github.com/BehaviorTree/BehaviorTree.ROS2) | ROS 2 Action、Service、Topic 的 BT wrapper。 | Jetson 已升级至 Ubuntu 22.04 / ROS 2 Humble，满足上游 ROS 版本要求；但当前任务复杂度尚未达到引入门槛，因此不进入 H 闭环或核心依赖。 |
| [EGO-Planner-Swarm](https://github.com/ZJU-FAST-Lab/ego-planner-swarm) | 未知障碍环境的在线重规划和多机规划。 | 仅在任务实际需要在线避障或多机时，以独立进程、单独 manifest 和 navigation adapter 接入。不得直接发布 `/fmu/in/*`；引入前审查 GPL-3.0 影响和 ROS 2 分支的 DDS 假设。 |
| [GCOPTER](https://github.com/ZJU-FAST-Lab/GCOPTER) | MINCO 轨迹优化、走廊约束和动力学约束。 | 作为未来优先评估的平滑轨迹优化后端，但它不是完整导航框架。必须先建立地图/走廊输入、带时间戳轨迹输出和 gateway 轨迹跟踪契约。 |
| [Fast-Drone-250](https://github.com/ZJU-FAST-Lab/Fast-Drone-250) | 整机装配、供电、传感器、VINS 外参标定和实机调试流程。 | 只作为硬件与调试清单参考，不复制其旧固件、PX4 1.11 参数或绕过检查的配置；转载和代码使用还需遵守其 README 所述限制。 |

任何第三方后端都必须使用独立可选 manifest 和精确提交。未经当前工作区构建、许可证、坐标、时间、QoS
和运行时验证，不得进入核心发布清单。

## 3. 接口演进原则

### 3.1 第一阶段保留现有飞行能力接口

`/offboard/execute_flight` 的 `TAKEOFF`、`GOTO`、`HOLD`、`RETURN_HOME` 和 `LAND` 足以完成固定航点的
H 任务闭环。第一条纵向链路完成前，不增加通用插件系统或轨迹接口。

### 3.2 动态任务必须在 navigation 层形成新能力

D 任务的车辆跟踪和动态降落不能长期依靠高频取消并重发 `GOTO`。H 任务闭环稳定后，再冻结以下候选
能力的输入、反馈、取消和失效语义：

- `FollowTarget`：消费带新鲜度和速度语义的目标观测，处理短时丢失、重捕获和退出策略。
- `LandOnTarget`：区分飞机定位失效与目标丢失，并保留 Land 请求后的不可取消语义。
- `ExecuteTrajectory`：承载带时间戳、坐标系、速度/加速度和有效区间的轨迹。

EGO-Planner 或 GCOPTER 只能生成导航结果；轨迹验证、跟踪和向 PX4 发布 setpoint 仍由 `offboard_cpp`
负责，以保持单 writer。

### 3.3 任务编排和飞行安全不得混合

- FSM 或未来的 BT 决定“下一项能力是什么”，不实现 Offboard 握手、ACK、RC 门、Land 或 setpoint 发布。
- `boomboom_mission_core` 继续统一任务取消、失败和完成结果；同一个任务不得同时维护等价的 FSM 和 BT
  两套策略真相。
- BT 节点若被引入，只能作为异步 ROS 2 Action/Service 客户端，不直接依赖 `px4_msgs`。

### 3.4 多机能力通过 namespace 演进

当前绝对话题名服务于单机原型。进入多机或多实例仿真前，应先将自研节点改为可 remap 的相对名称，
由 launch 提供 `/uav/<id>` namespace；不得通过复制包或修改源码常量区分飞行器。该改动不是当前 H
闭环的前置条件。

## 4. 分阶段实施路线

### A. H 任务模拟纵向闭环

不连接 PX4，不引入第三方依赖，先完成：

1. 外部 START、取消和任务终态输入。
2. 覆盖规划结果到连续 `ExecuteFlight` goal 的映射。
3. Action goal accepted、feedback、success、abort、cancel 和 timeout 到 FSM event 的映射。
4. fake flight Action server、fake perception 输入和确定性任务场景测试。
5. `WAIT -> PLAN -> TAKEOFF -> PATROL -> RETURN -> LAND -> COMPLETE` 以及失败、取消路径。

完成标准：无需 PX4 即可从外部 START 进入确定终态；测试期间不存在 `/fmu/in/*` writer。

### B. 标准构建与可复现基线

在独立干净构建目录完成目标九包一次性 `colcon build/test`，审查每个嵌套仓库改动，把
`communication`、`ti` 等真实可取得提交写入 manifest，并要求 `verify_repos.py` 通过。

### C. 新 gateway 未解锁 SITL

验证 ROS graph、QoS、单 writer、Action 接受/拒绝/取消、PX4 ACK、状态转换和故障分支。该阶段保持未解锁；
进入 RC 解锁、QGC 模式操作或飞行前必须另行取得操作员确认。

### D. D 任务和动态能力

先用模拟目标和设备回执冻结 `FollowTarget`、`LandOnTarget` 或轨迹契约，再选择是否需要 GCOPTER 或
EGO-Planner。规划器选择不得早于输入地图、实时预算、坐标系和输出轨迹验收标准。

### E. 目标硬件

完成真实 VIO 动态、延迟、reset、外参和 EKF2 验证，并在升级后的 Jetson Orin Nano Ubuntu 22.04 / ROS 2
Humble 上重新建立工作区构建、DDS 和无桨地面联调证据。BehaviorTree.ROS2 的版本条件已满足，但其采用
仍由任务并行、重试和 Fallback 复杂度决定，不能仅因系统升级而进入目标基线。

## 5. 当前明确不做

- 不把 Aerostack2、BehaviorTree.CPP 或规划器变成核心框架依赖。
- 不在任务、感知、规划器或设备节点中增加 PX4 控制 writer。
- 不在当前纵向闭环中同时更换 direct-Offboard 为 PX4 External Mode。
- 不为假设中的多机、插件热加载或算法切换预先建立复杂抽象。
- 不把离线测试、legacy SITL 或合成视觉证据外推为新 gateway、TI、Jetson 或实机通过。
