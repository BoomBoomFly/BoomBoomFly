# BoomBoomFly 第一阶段实施计划

## 1. 计划定位

本文中的“第一阶段”指 `BoomBoomFly_统一技术路线.md` 第 2 节定义的最小飞行闭环，
不是只指实施顺序中的 `Phase 1: common`。实现范围覆盖统一路线的 Phase 0–5：

```text
路线冻结与清理
→ common 最小核心
→ offboard_cpp SITL 闭环
→ px4_vision_bridge 数据链
→ bringup 与双环境配置
→ 实机地面及受控飞行门禁
```

用户已确认并执行本计划。Phase 0–4 的源码迁移、重构、包级构建和单元测试已经完成；
初步 SITL DDS/readiness 和一次正常最小闭环已经完成，mission node 已回到 `READY`。故障注入、
视觉融合、Foxy 和实机操作仍未执行；Phase 5 只生成现场门禁清单。

信息优先级沿用统一技术路线：现行需求与硬件约束 > `handoff.md` > 统一技术路线的
第一阶段选择 > 已归档历史资料的机制研究 > 旧代码。旧代码只提供外部约束和历史证据，
不作为新结构的兼容目标。

## 2. 已确认并已实施的决策

| 编号 | 决策 | 第一阶段采用值 |
|---|---|---|
| D1 | PX4 控制接口 | 直接使用 `px4_msgs + uXRCE-DDS + Offboard`，不依赖 Custom Mode/ModeExecutor |
| D2 | 控制所有权 | 只有一个 `offboard_mission_node` 写三个 `/fmu/in/*` 控制话题 |
| D3 | `communication` | 第一阶段无 ROS 运行节点、无 START 协议，只保留包/仓库边界 |
| D4 | `common` | 同一仓库内 `C99 core + ROS 2 adapter`，core 可被 STM32 直接纳入 |
| D5 | 公共信息模型 | `domain + condition + detail`、`state + reason + entered_at`、fault bitmask、结构化 event 分离 |
| D6 | 坐标系 | 任务内部 NED/FRD；原始 VIO 只经 bridge 注入 EKF2，控制只读融合后的本地状态 |
| D7 | 视觉后端 | 第一阶段仅 DDS `VehicleOdometry`，不保留 MAVROS 双后端 |
| D8 | 旧资产 | `hardware.pdf` 默认保留不动；未确认价值的标定、STM32 代码不作为新设计输入 |
| D9 | 验证授权 | 确认本文后可执行编译、单元/节点测试和 SITL；实机解锁/飞行仍需单独现场授权 |

不采用：旧 START/session/epoch 链、authority lease、运行时 ROS graph 扫描、多任务 FSM、
七 Mode 蓝图、自动 ARM/DISARM/Kill、MAVROS/DDS 双写、lifecycle、composition、插件框架、
通用 backend、未知串口协议和旧接口兼容层。

## 4. 第一阶段范围

### 4.1 必须完成的任务路径

```text
BOOT
→ WAIT_DISARMED
→ WAIT_LOCALIZATION
→ READY
→ OFFBOARD_PRESTREAM
→ REQUEST_OFFBOARD
→ TAKEOFF
→ HOVER
→ RETURN_LOCAL
→ LAND_REQUEST
→ WAIT_LANDED
→ COMPLETE
→ WAIT_DISARMED
```

任务参数默认语义：相对接受 RC 解锁沿时冻结的本地 home 起飞 `1.5 m`，到位稳定后悬停
`60 s`，保持高度返回 home x/y，随后请求 Land 并等待 PX4 landed 与解除解锁事实。

### 4.2 强制不变量

1. 节点启动后先观察至少一次 `ARMING_STATE_DISARMED`；启动时已解锁不能触发任务。
2. 只有 `latest_arming_reason` 为 `STICK_GESTURE` 或 `RC_SWITCH` 的解锁上升沿可启动。
3. 定位未健康时发生的解锁沿不缓存，必须解除解锁后重新触发。
4. 程序不发送 ARM、DISARM 或 Kill；Kill 直接由 RC 映射到 PX4。
5. ACK 接受与 `VehicleStatus.nav_state == OFFBOARD` 两个事实都成立才进入 TAKEOFF。
6. 任一生产 PX4 控制输入话题只有一个 writer。
7. 飞行反馈只使用 PX4 EKF2 的 `VehicleLocalPosition`，不直接闭环原始 VIO。
8. 定位有效才返回本地 home；持续失效时请求原地 Land，不盲目返航。
9. 用户切出 Offboard 或 PX4 failsafe 后停止本轮任务，不自动抢回。
10. 本地位置 reset 时同步修正冻结 home 与活动目标。
11. launch 不自动解锁，不用固定延迟代替 readiness。
12. 节点崩溃安全依赖 PX4 Offboard-loss/failsafe，不依赖析构或最后一条命令必达。

### 4.3 明确不做

- 目标识别、搜索、追踪、投放和动态降落；
- 串口上位机 START、旧车机协议或 communication 运行节点；
- Custom Mode/ModeExecutor、MAVROS 后端或 legacy 双后端；
- 自动解锁/解除解锁/Kill；
- 复杂 supervisor、lease、插件、生命周期和通用序列化；
- Foxy 结果由 Humble 推断通过；Foxy 必须在目标环境单独验证。

## 5. 目标目录与职责

### 5.1 `common`

```text
common/
├── core/
│   ├── CMakeLists.txt
│   ├── include/boomboom_common/{status,state,fault,event,log}.h
│   └── src/
├── ros2/
│   ├── include/boomboom_common_ros2/
│   └── src/
├── msg/{Status,State,Faults,Event}.msg
├── test/
├── CMakeLists.txt
├── package.xml
└── README.md
```

core 只使用 C99、固定宽度整数、POD 和调用方提供的 sink；不依赖 ROS/PX4/HAL、异常、
RTTI、动态内存、文件系统或 UART。第一版枚举只覆盖第一阶段实际出现的 mission、vision、
输入过期、命令拒绝、失权、failsafe、定位失效与 reset 事件，不创建全项目错误码大全。

### 5.2 `offboard_cpp`

```text
offboard_cpp/
├── include/offboard_cpp/
│   ├── mission_controller.hpp
│   ├── mission_types.hpp
│   ├── px4_interface.hpp
│   └── offboard_mission_node.hpp
├── src/{mission_controller,px4_interface,offboard_mission_node,main}.cpp
├── config/{mission_common,sitl,hardware}.yaml
├── launch/offboard_mission.launch.py
├── test/
├── hardware/hardware.pdf
├── CMakeLists.txt
├── package.xml
└── README.md
```

`MissionController` 是无 ROS/PX4 依赖的值输入/值输出状态机；`Px4Interface` 负责 QoS、
消息、时间戳、ACK 和 PX4 状态快照；节点只做参数、20 Hz steady-clock 驱动、二者连接和
common 事件映射。不增加虚接口、依赖注入容器或多 backend。

### 5.3 `px4_vision_bridge`

```text
px4_vision_bridge/
├── include/px4_vision_bridge/
│   ├── vision_sample.hpp
│   ├── odometry_converter.hpp
│   └── px4_odometry_builder.hpp
├── src/{odometry_converter,px4_odometry_builder,vision_bridge_node,main}.cpp
├── config/{vision_common,sitl,hardware}.yaml
├── launch/vision_bridge.launch.py
├── test/
├── CMakeLists.txt
├── package.xml
└── README.md
```

只实现 `nav_msgs/Odometry → px4_msgs/VehicleOdometry → /fmu/in/vehicle_visual_odometry`。
位置、姿态、线速度、角速度和协方差全部按 ENU/FLU → NED/FRD 契约转换；姿态使用旋转
复合，不交换四元数分量。采样时间和生成时间分开，输入 frame、有限值、四元数、时间
单调性和 freshness 均在发布前检查。

### 5.4 `communication`

第一阶段不包含 `package.xml` 或可运行节点。旧 `Serial/`、重复的 `common/`、
`car_link_protocol.md` 和 START/session/epoch 逻辑均属于删除候选；确认后删除仍可从 Git
历史恢复。仓库只保留简短 README，说明未来结构化 state/fault/event → 编码器 → 串口
transport 的边界。未知协议不预建字段、CRC 框架或重连状态机。

### 5.5 `px4_bringup`

```text
px4_bringup/
├── launch/{sitl,hardware}.launch.py
├── config/
│   ├── common/{mission,vision_bridge}.yaml
│   ├── sitl/{mission,vision_bridge,px4.params}
│   └── hardware/{mission,vision_bridge,px4.params}
```

bringup 只做进程编排、namespace、设备路径和参数选择。节点自己依据数据新鲜度进入 READY；
launch 中不复制业务参数、不自动 ARM、不以 `TimerAction` 推断依赖已经就绪。

### Phase 5：实机门禁（不由代码代理自动执行）

```text

→ 手持位移/旋转
→ 无桨 PX4/DDS/RC 联调
→ Kill/人工接管/定位中断/Jetson 退出演练

→ 60 s 悬停
```

实机飞行或替用户判断现场安全。

## 8. 已执行的多代理编排

执行窗口使用根协调器加 3 个工作代理；根和工作代理均指定 `gpt-5.6-terra`、
`reasoning_effort=high`。若显式覆盖模型，工作代理使用自包含提示并设置非 full-history fork。

### 8.1 固定文件所有权

| 执行者 | 独占写入范围 | 首轮任务 |
|---|---|---|
| 根协调器 | 根仓库 `docs/`、`manifests/`、`Scripts/`、根 README；跨包集成 | 快照、迁移协调、接口冻结、最终集成与验收 |
| Worker A | `common/**` | C99 core、ROS adapter、消息与测试 |
| Worker B | `offboard_cpp/**` | MissionController、Px4Interface、节点、配置与测试 |
| Worker C | `px4_vision_bridge/**` | 转换、DDS builder、节点、配置与测试 |

任何 worker 不得编辑其他 worker 的目录、根 manifest 或共享脚本。跨包依赖变更通过根协调器
合并，避免三个代理同时修改同一 CMake、消息定义或 launch。

### 8.2 波次安排

**Wave A：串行前置**

- 根协调器完成 Gate 0、视觉仓库迁移和目标骨架；
- 根协调器冻结 common 头文件/消息的最小契约；
- 确认无文件所有权冲突后再启动 3 个 worker。

**Wave B：三路并行**

- Worker A：Phase 1 全部；
- Worker B：Phase 2 的纯状态机和 PX4 边界；
- Worker C：Phase 3 的纯数学与 DDS bridge；
- 根协调器持续做只读审查和接口一致性检查，不抢改 worker 文件。

**Wave C：依赖收口并行**

- Worker A 完成 common 与两个消费者的编译契约核对；随后处理 `communication` 的已批准清理；
- Worker B 完成 offboard 节点级测试与故障矩阵；
- Worker C 完成 bridge 节点级测试后，转去独占修改 `px4_bringup/**`；
- 根协调器处理 manifests、脚本、README 和跨包 launch 接线。

**Wave D：根协调器集成**

- 等全部 worker 停止写入后统一查看 diff；
- 逐包构建/测试，再做完整 colcon，不让并行构建争用同一 build/install/log；
- 最后运行 SITL 和故障注入，生成证据摘要；
- Phase 5 只输出现场 runbook 和待操作员执行的检查表。

### 8.3 并行冲突规则

1. 不并行移动同一仓库或删除公共目录。
2. 不并行运行共享 colcon build、clean 或同一 ROS_DOMAIN_ID 的 SITL。
3. worker 不提交、不 push、不清理他人工作树。
4. 发现新用户输入或重叠修改立即停止对应文件写入并通知根协调器。
5. 每个 worker 交付：变更文件、保留的不变量、运行命令、结果、未验证项。

### 9.2 SITL 验证

- 正常路径：prestream → Offboard → 1.5 m → 60 s → home → Land；
- 启动时已解锁；定位未就绪时解锁；非 RC 来源解锁；
- Offboard ACK 拒绝/超时以及 ACK 接受但 nav state 未切换；
- 状态/定位过期、坐标 reset、用户切出 Offboard、PX4 failsafe；
- 定位有效时取消返回 home，定位失效时原地 Land；
- mission node 退出后的 PX4 Offboard-loss 收口；
- bridge 的延迟、时间倒退、坏四元数和 reset 输入。

SITL 的正常启动仍必须证明 `latest_arming_reason` 真的是 RC switch/stick。若当前仿真环境
只能产生 external command arm，不得给生产代码增加绕过开关；可先以纯逻辑/节点测试覆盖，
再用隔离的虚拟 RC 或现场 RC 完成真实来源验证。

|---|---|---|
