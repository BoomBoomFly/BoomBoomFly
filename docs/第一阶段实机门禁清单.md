# 第一阶段实机门禁清单

本清单不授权解锁、起飞或修改 PX4 参数。每一项均由现场操作员单独确认；任一失败都回到
上一层排查，不进入下一项。

当前软件证据：`px4_msgs`、`boomboom_common`、`px4_vision_bridge` 与 `offboard_cpp` 已在
Humble 构建；common 2/2、vision bridge 3/3、offboard controller 1/1 CTest 已通过。SITL
已确认关键 DDS 状态样本与 mission `READY`，但尚未验证 RC 解锁沿、Offboard、视觉融合、Foxy
或现场步骤，因此不替代本清单中的任何操作员批准。

## 0. 软件与配置

- 记录根仓库和每个嵌套仓库的 HEAD、工作区状态和 PX4/px4_msgs/Agent 固定提交。
- 确认唯一生产 writer：mission node 写三个控制输入，vision bridge 只写
  `/fmu/in/vehicle_visual_odometry`。
- 确认硬件 `vision_bridge.yaml` 的输入 frame、机体 frame、VIO 外参和时钟来源已由实际系统
  测得；未确认时不得放行自主飞行。
- 启动 PX4 后确认 `/fmu/out/timesync_status` 新鲜；bridge 在它缺失或过期时必须拒绝发布。

## 1. 无桨地面联调

- 由操作员启动 PX4、DDS Agent 与 `ros2 launch px4_bringup hardware.launch.py`；launch 不会
  自动解锁。
- 核对 mission node 首先停在 `WAIT_DISARMED`，随后在本地定位有效时才进入 `READY`。
- 用 RC 验证 Kill、人工模式切换和 Offboard 退出；程序不得重新请求 Offboard。
- 验证 RC 解锁前后仅接受 `STICK_GESTURE` 或 `RC_SWITCH` 的上升沿，且不会发布 ARM/DISARM/Kill。

## 2. 定位与失效演练

- 手持相机完成单轴位移、旋转、静止与延迟检查，确认 EKF2 输出的
  `VehicleLocalPosition` 有效且方向正确。
- 注入 VIO 停止、过期时间戳、坏四元数和 PX4 timesync 中断；bridge 应停止写入，mission 应
  请求原地 Land 而非盲目返航。
- 在无桨状态验证本地位置 reset 后冻结 home 与目标按 PX4 delta 同步修正。

## 3. 受控飞行

- 仅在定位、Kill、人工接管和 Offboard-loss 演练均通过后，进入系留或保护场地。
- 按顺序验证：1.5 m 起飞、稳定判据、60 s 悬停、水平返回本地 home、PX4 Land、操作员解除解锁。
- 保存 ROS 事件/故障、VehicleStatus、VehicleLocalPosition、VehicleOdometry、VehicleCommandAck
  和 PX4 ulog；记录任何异常的时间点。
