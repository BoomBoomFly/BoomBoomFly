# BoomBoomFly 工作区架构

本文只定义长期仓库职责、依赖方向、接口和安全不变量。外部项目的借鉴、接入条件和阶段顺序见
[参考框架采用与演进路线](参考框架采用与演进路线.md)，当前完成度、验证证据和停止条件见
[当前交接](handoff.md)，实机操作只按[第一阶段实机门禁清单](第一阶段实机门禁清单.md)推进。

## 1. 工作区布局

```text
BoomBoomFly/
├── manifests/                       # vcstool 精确提交清单
├── Scripts/                         # 拉取、构建、验证和仿真入口
├── docs/                            # 系统级架构、交接和门禁
└── px4/
    ├── upstream/
    │   ├── PX4-Autopilot/
    │   └── Micro-XRCE-DDS-Agent/
    └── px4_ws/src/
        ├── external/
        │   ├── px4_msgs/
        │   └── 可选第三方规划/感知依赖
        └── boomboom/
            ├── common/
            ├── communication/
            ├── offboard_cpp/
            ├── px4_vision_bridge/
            ├── px4_bringup/
            ├── ti/
            ├── perception/          # 任务级目标感知独立仓库
            └── embedded_systems/    # 嵌入式、小车和硬件执行独立仓库
```

顶层仓库不吸收嵌套仓库历史。每个自研仓库保留自己的 `.git`、远端、分支和工作树；只有形成远端可取得、
经过验证的真实提交后，才能把 SHA 写入 manifest。

目标部署基线为 Jetson Orin Nano、Ubuntu 22.04 和 ROS 2 Humble。开发机与目标机即使使用相同 ROS 2
发行版，也必须分别保留构建、DDS、VIO、无桨联调和运行时证据。

## 2. 仓库职责

| 仓库 | 唯一职责 |
|---|---|
| `BoomBoomFly` | 管理清单、脚本、版本、构建、仿真和系统文档。 |
| `common` | 定义公共 ROS 2 `msg/srv/action`、状态码和错误码；保留不依赖 ROS 的 C99 core。 |
| `offboard_cpp` | 通用 PX4 飞行网关，独占三个 PX4 Offboard 控制输入。 |
| `px4_vision_bridge` | 把外部里程计或兼容视觉输入送入 PX4 EKF2，不控制飞行。 |
| `px4_bringup` | 启动 DDS Agent、飞行网关和视觉桥，不承载任务状态机。 |
| `communication` | 定义地面站、无人机和小车之间的版本化通信语义，不绑定具体传输。 |
| `ti` | 提供导航适配、H 任务协调器和 D 任务的 ROS-free 状态机原型。 |
| `perception` | 产生动物、小车和降落标志等带时间与有效性语义的观测。 |
| `embedded_systems` | 汇集嵌入式驱动与固件、小车本地控制，以及激光器、投放器等硬件命令执行与结果回报。 |

## 3. 依赖与控制权

```text
communication ─┐
               ├──> ti 任务状态机 ───> embedded_systems
perception ────┘          │
                          v
               boomboom_navigation
                          │
                          v
                    offboard_cpp
                          │
                          v
                         PX4

VIO/相机 ──> px4_vision_bridge ──> PX4 EKF2
```

必须保持：

- `ti` 不依赖 `px4_msgs`，也不发布任何 `/fmu/in/*` 话题。
- H/D 两个任务包互不依赖；已接入飞行的 H 任务通过 `boomboom_navigation` 使用 Action。D 尚无运行节点，
  未来接入飞行时也必须经过该适配层。
- 高级规划器只能由 `boomboom_navigation` 适配，任务状态机不得直接依赖第三方规划器。
- `offboard_cpp` 不依赖 `ti`，并且只有一个运行实例可以写
  `/fmu/in/offboard_control_mode`、`/fmu/in/trajectory_setpoint` 和 `/fmu/in/vehicle_command`。
- `px4_vision_bridge` 只写估计器输入 `/fmu/in/vehicle_visual_odometry` 或 MAVROS 视觉输入，不取得飞行控制权。
- 感知只输出观测；`embedded_systems` 的设备和小车执行均不得自行改变无人机飞行状态。

## 4. 公共接口

`common` 是公共信息模型的唯一所有者：

- `/offboard/execute_flight` 使用 `ExecuteFlight` Action，命令为 `TAKEOFF`、`GOTO`、`HOLD`、
  `RETURN_HOME`、`LAND`。
- `/boomboom/flight_state` 发布飞行执行器的 EKF2 状态快照。
- `/boomboom/observations/target` 只承载目标观测。
- `/boomboom/devices/command` 与 `/boomboom/devices/ack` 承载设备命令及回执。

`devices` 话题命名表示逻辑设备接口，不要求与承载实现的 `embedded_systems` 仓库同名。

`communication` 只定义地面站、无人机和小车的版本、会话、序列号、幂等和断连语义。它不得复制 ROS
消息作为另一套信息模型，也不得把内存 C struct 直接当作线格式。

## 5. 飞行网关安全契约

- PX4/RC 始终拥有 ARM、DISARM、Kill、人工接管和 failsafe 的最终权限；程序不发送 ARM、DISARM 或 Kill。
- 首个 `TAKEOFF` 必须先观察一次 `DISARMED`、确认 EKF2 本地位置和 heading 健康，再等待来源为
  `STICK_GESTURE` 或 `RC_SWITCH` 的解锁上升沿。
- 请求 Offboard 前以 20 Hz 预发送位置 setpoint 至少 1 s；必须同时获得匹配 ACK 和实际
  `nav_state == OFFBOARD`。
- home 在启动沿冻结；PX4 位置或 heading reset 时同步修正 home 与活动目标。
- 人工退出 Offboard 或 PX4 failsafe 后不重新抢权；定位失效时请求原地 Land，不盲目返航。
- 新 Action gateway 在 Land 前取消动作时转为原地 HOLD，不自动返航；Land 请求后不可取消，且完成必须
  等待请求之后的新 `landed = true` 样本。
- `offboard_gateway_node` 是唯一保留的 PX4 控制写入节点，不再提供旧版 mission 回放入口。

## 6. 坐标、视觉与时间

- 飞行网关和 PX4 侧使用本地 NED/FRD；DDS 视觉输入的 ENU/FLU 转换由 `px4_vision_bridge` 完成。
- 姿态、速度和协方差必须按明确的 world/body frame 完整变换，不能只交换轴或改变符号。
- DDS backend 只在输入和 `TimesyncStatus` 新鲜有效时发布，并把样本时间映射到 PX4 boot-time。
- DDS 与 MAVROS backend 互斥。MAVROS 兼容路径只发布新的 `PoseStamped` 样本，不提供速度测量。
- MAVROS 路径不补偿相机到机体的平移；hardware profile 必须使用已标定的
  `odom_frame -> base_link` TF，并保持 `require_body_source_frame=true`。
- 宿主 realtime 跳变必须在系统时钟层修复，不得通过放宽 PX4、bridge 或 MAVROS 阈值掩盖。

## 7. TI 结构与演进

```text
ti/
├── boomboom_navigation/            # 网格、航点、跟踪和降落引导适配
├── ti_2025/                        # 野生动物巡查（ROS 包 boomboom_task_h）
├── ti_2026/                        # 陆空协同（ROS 包 boomboom_task_d）
└── docs/                            # 新人、接口和依赖说明
```

所有自研包的 launch 文件统一位于 `px4_bringup/launch/`；其中 TI 的 SITL/硬件任务级入口为
`ti_task.launch.py`，当前只启动 H，参数位于 `px4_bringup/config/ti/task_h.yaml`。D 在真实流程明确前只保留
ROS-free 状态机，不提供空节点或启动配置。其他功能包只保留节点、库和自身配置，
不再安装 launch 文件。

第一阶段使用可单元测试的 C++ FSM。只有并行、重试和条件分支显著增长后，才评估
BehaviorTree.CPP。EGO-Planner/GCOPTER 只允许作为可选 navigation backend，不能成为任务核心依赖。

## 8. 自有框架演进原则

- 自有框架以稳定能力接口和依赖方向为核心，不以统一基类、插件系统或聚合第三方框架为目标。
- 当前 direct-Offboard gateway 保持飞行控制基线；PX4 ROS 2 Interface Library 只能在独立分支和匹配
  v1.16.2 的精确提交上评估，不能与当前 gateway 同时成为生产 writer。
- 任务策略继续优先使用 ROS-free、可单元测试的 FSM；未来的 BT 只能替换任务策略，不能进入飞行安全层。
- 动态跟踪、动态降落和轨迹飞行先在 `boomboom_navigation` 冻结能力契约，再选择规划算法后端。
- EGO-Planner、GCOPTER 等第三方算法只能输出导航结果；setpoint 验证、跟踪和 PX4 发布仍归
  `offboard_cpp`。
- 多机需求通过相对接口名、launch remap 和 `/uav/<id>` namespace 演进，不通过复制包或增加控制 writer。

具体参考仓库采用边界和分阶段验收标准见[参考框架采用与演进路线](参考框架采用与演进路线.md)。

## 9. 复现与证据边界

- 项目自有的 README、架构、交接和操作说明统一使用简体中文；命令、路径、代码标识符、ROS/PX4
  接口名及外部项目专名保持原样，避免翻译后失去可执行性或可检索性。
- 可选规划器使用单独清单和精确提交，通过 navigation 适配器接入。
- `verify_repos.py` 通过之前，工作树不能称为可复现发布基线。
- 离线构建、单测和静态检查不等于 ROS 图、SITL、目标 Jetson/Humble、EKF2 动态融合或实机验证。
- 新 gateway 与 TI 任务链必须通过独立 SITL 和实机门禁后，才能进入实机验证。
