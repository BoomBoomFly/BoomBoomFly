# 零基础开源项目阅读与学习路线

本文面向没有编程、ROS 2 或无人机基础的接手者。学习材料来自维护良好、文档明确的 GitHub 项目，
不以 BoomBoomFly 源码作为教材，也不安排小练习、代码修改、构建、仿真或实机操作。

BoomBoomFly 的实时状态、已验证证据和下一步只看[当前交接](handoff.md)；长期接口与安全边界只看
[工作区架构](工作区架构.md)。完成本文的阅读不代表获得运行 SITL、解锁或操作实机的授权。

## 1. 使用方法

推荐按阶段顺序阅读，不要求从头到尾通读任何大型仓库。每个项目统一按以下顺序进入：

```text
README
  -> 官方概念文档
  -> 仓库目录
  -> 最小示例
  -> 公共接口
  -> 核心实现外壳
  -> 测试
  -> launch / config
```

每一阶段的“完成标志”只用于判断是否可以继续阅读，不是作业或考试。遇到数学、模板、控制器或底层中间件
细节时，先确认它是否列在“暂时跳过”中；零基础阶段的目标是建立正确系统图，而不是一次读懂全部实现。

### 1.1 项目选择规则

- 优先官方组织、原作者或长期维护团队的仓库和文档。
- ROS 2 项目固定到 `humble`；PX4 固定到 `v1.16.2`，不把默认 `main` 当作同一版本。
- Star 数只作参考；版本、维护状态、文档质量和许可证边界更重要。
- “用于学习”不等于“建议加入 BoomBoomFly 依赖”。
- GPL 或自定义许可证项目只链接和阅读；未来复制、修改或集成前必须重新审查许可证。
- 移动分支用于了解后续修复；稳定阅读优先固定 tag，并记录本文核验日期。

### 1.2 总体顺序

| 阶段 | 主题 | 主线项目 | 建议阅读量 |
|---|---|---|---|
| 0 | 终端与 Git | Missing Semester、Pro Git | 1–2 周 |
| 1 | C++、CMake 与测试 | C++ 基础材料、CMake Tutorial、GoogleTest | 4–6 周 |
| 2 | ROS 2 通信与包结构 | `ros2/examples`、`ros2/demos` | 3–4 周 |
| 3 | 机器人系统分层 | `ros2_control_demos`、Navigation2 | 2–3 周 |
| 4 | PX4 与 ROS 2 | PX4-Autopilot、`px4_msgs` | 3–4 周 |
| 5 | VIO | OpenVINS | 2–3 周 |
| 6 | 无人机自治与规划 | Aerostack2；GCOPTER/EGO 选读 | 2–3 周 |
| 7 | 项目接手 | BoomBoomFly 交接与架构文档 | 1–2 天 |

时间以每天约 1–2 小时阅读估算，只表达内容量，不是截止日期。是否进入下一阶段以能否解释本阶段关键问题
为准。

## 3. 阶段 1：C++、CMake 与测试

开源项目不能替代系统的 C++ 入门教材。零基础接手者应先通过结构化教材理解变量、控制流、函数、类、
头文件、源文件、引用、指针和 `const`，再进入以下 GitHub 项目。本文不指定商业教材，也不要求此阶段阅读
完整语言标准。

### 3.1 C++ Core Guidelines

- 仓库：[`isocpp/CppCoreGuidelines`](https://github.com/isocpp/CppCoreGuidelines)
- 版本：`master`；旧 `v0.8` tag 不代表当前内容。
- 定位：选读和长期参考，不是 C++ 语法入门教材。
- 许可证：项目自定义许可，仅允许个人或内部业务用途；只链接阅读，不大段转载。

先看 README 和[浏览版正文](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)，再选读 `In`、`P`、
`I`、`F`、`R`、`ES` 和 `SF` 中与接口、函数、资源管理、表达式和源文件有关的章节。初期只关注
`const`、参数传递、作用域、RAII、所有权和避免裸 `new/delete`。

暂时跳过并发、模板元编程、性能、GSL enforcement、工具脚本和规则争论。

完成标志：能解释值、引用和指针参数的差异，知道所有权与 RAII 的用途，并理解公共接口为什么应减少
可变状态。

### 3.2 CMake

- 主线：[`Kitware/CMake` 官方 Tutorial](https://github.com/Kitware/CMake/tree/master/Help/guide/tutorial)
- 辅助示例：[`pr0g/cmake-examples`](https://github.com/pr0g/cmake-examples)
- 辅助示例版本：`main`，阅读时记录 commit；许可证 MIT。

官方 Tutorial 优先读 Step 0、1、4、5 和 8 的 Background 与 Solution。辅助仓库只读根 README、
`examples/core/README.md`、header-only、static、shared，最后再看 installing。辅助仓库作者明确说明自己并非
CMake 专家，示例可能有错误，因此不能取代 Kitware 官方文档。

暂时跳过 shared export、FetchContent、ExternalProject、复杂安装导出、工具脚本和格式化配置。

完成标志：能解释 source/build/install tree、configure/build、target 与源文件列表、静态库、动态库、
header-only 库，以及 `PRIVATE/PUBLIC/INTERFACE` 的传播方向。

### 3.3 GoogleTest

- 仓库：[`google/googletest`](https://github.com/google/googletest/tree/v1.18.0)
- 版本：`v1.18.0`，要求至少 C++17。
- 定位：单元测试主线。
- 许可证：BSD-3-Clause。

阅读顺序：

1. README。
2. [`docs/quickstart-cmake.md`](https://github.com/google/googletest/blob/v1.18.0/docs/quickstart-cmake.md)。
3. [`docs/primer.md`](https://github.com/google/googletest/blob/v1.18.0/docs/primer.md)。
4. `googletest/samples/sample1_unittest.cc`。
5. `googletest/samples/sample3_unittest.cc`。
6. `googletest/CMakeLists.txt`。

暂时跳过 GoogleMock、advanced guide、death test、typed/parameterized test、内部实现、Bazel 和 CI。

完成标志：能解释 test、test suite、fixture、`EXPECT_*`、`ASSERT_*`、`gtest_main`、测试发现、退出码和
CTest 各自负责什么。

### 3.4 `{fmt}`

- 仓库：[`fmtlib/fmt`](https://github.com/fmtlib/fmt/tree/12.2.0)
- 版本：`12.2.0`。
- 定位：完成 C++、CMake 和 GoogleTest 基础后的真实项目选读。
- 许可证：代码为 MIT；部分格式语法文档另受 PSF 许可证约束。

阅读顺序为 README 的 Features/Examples、`doc/get-started.md`、`include/fmt/base.h` 公共入口、根
`CMakeLists.txt` 中的 target、`src/format.cc`、`test/base-test.cc` 和 `test/format-test.cc`。

暂时跳过浮点格式化、Dragonbox、复杂 `constexpr`/模板实现、benchmark、fuzz 和 `support/`。

完成标志：能解释公共头文件与实现文件、编译库与 header-only、CMake target usage requirements，以及
测试如何约束公共 API。

完成标志：能解释能力 Action、任务编排、planner server、controller server 和算法 plugin 的依赖方向。

## 6. 阶段 4：PX4 与 ROS 2

本阶段以 `PX4-Autopilot v1.16.2 + px4_msgs v1.16.2 + ROS 2 Humble` 为统一阅读基线。只有需要跟踪
1.16 后续补丁时，才改读两个仓库的 `release/1.16` 移动分支。

### 6.1 PX4-Autopilot

- 仓库：[`PX4/PX4-Autopilot`](https://github.com/PX4/PX4-Autopilot/tree/v1.16.2)
- 版本：`v1.16.2`。
- 定位：PX4 主线。
- 许可证：BSD-3-Clause。

阅读顺序：

1. 根 README。
2. `docs/en/concept/architecture.md`。
3. `docs/en/middleware/uorb.md`。
4. `docs/en/ros2/user_guide.md`。
5. `docs/en/middleware/uxrce_dds.md`。
6. `docs/en/flight_modes/offboard.md`。
7. `docs/en/ros2/offboard_control.md`。
8. `src/modules/uxrce_dds_client/dds_topics.yaml`。
9. 与 Offboard 有关的少量 `msg/*.msg`。
10. 最后才看 `uxrce_dds_client` 和 `commander` 的相关源码外壳。

必须理解：client 在 PX4，Agent 在伴随计算机；`dds_topics.yaml` 决定实际暴露的 topic 子集；
`/fmu/out/*` 是 PX4 发布，`/fmu/in/*` 是 PX4 接收；`px4_msgs` 含有全部定义不代表全部都经 DDS 暴露。

暂时跳过 boards、NuttX、驱动、EKF2 内部、控制器数学、完整 commander、固定翼和 VTOL 路径。

Agent 版本必须结合安装方式理解：PX4 `release/1.16` 的 standalone 入口可使用 v2.4.3，而 ROS 2 Humble
colcon workspace 的兼容路径使用 v2.4.2，不能脱离场景只记一个版本号。

完成标志：能画出 `uORB <-> uXRCE-DDS client <-> Agent <-> ROS 2`，并解释 Offboard setpoint、模式请求、
ACK 与实际飞行状态之间不是同一件事。

### 6.2 `px4_msgs`

- 仓库：[`PX4/px4_msgs`](https://github.com/PX4/px4_msgs/tree/v1.16.2)
- 版本：`v1.16.2`；移动分支为 `release/1.16`。
- 定位：PX4/ROS 2 接口主线。
- 许可证：BSD-3-Clause。

阅读顺序为 README、`package.xml`、`CMakeLists.txt`，再读 `OffboardControlMode.msg`、
`TrajectorySetpoint.msg`、`VehicleCommand.msg`、`VehicleCommandAck.msg`、`VehicleStatus.msg` 和
`VehicleOdometry.msg`，并与 PX4-Autopilot 中的同名定义对照。

暂时跳过全部消息通读、生成代码、release 和 CI 工具。`main` 只匹配 PX4 `main`；初学路线坚持完全匹配
tag，不依赖 message translation 掩盖版本混用。

完成标志：能解释 ROS 2 interface package 如何生成语言接口，以及消息定义匹配为什么是 PX4/ROS 2 通信
的前置条件。

### 6.3 `px4_ros_com`

- 仓库：[`PX4/px4_ros_com`](https://github.com/PX4/px4_ros_com/tree/release/1.16)
- 版本：`release/1.16`，没有对应 v1.16 的正式 tag。
- 定位：选读和历史示例，不是当前 uXRCE-DDS 桥接必需件。

暂时跳过 Python Offboard、旧 bridge 生成脚本和旧 Fast-RTPS 时间同步逻辑。Offboard 示例包含模式切换与
解锁命令，本文只安排阅读，不安排运行。

完成标志：能从示例中辨认 ROS 2 publisher/subscriber、PX4 消息、QoS 和坐标转换，同时知道该仓库不是
必须部署的桥接服务。

### 6.4 PX4 ROS 2 Interface Library

架构自动变成项目迁移建议。

## 7. 阶段 5：视觉惯性定位

### 7.1 OpenVINS

- 仓库：[`rpng/open_vins`](https://github.com/rpng/open_vins/tree/v2.7)
- 版本：`v2.7`；较新修复再补看 `master`。
- 定位：VIO 数据流主线，但零基础只读高层。
- 许可证：GPL-3.0。

阅读顺序：

1. `ReadMe.md`。
2. 官方 Getting Started 的 High-level overview。
3. `config/` 中相机、IMU、标定和 topic 的输入方式。
4. `ov_msckf/src/run_subscribe_msckf.cpp` 的 node、配置、`VioManager` 与可视化边界。

6. `ov_msckf/src/core/VioManager.*` 的结构。
7. `State`、`Propagator` 和 `UpdaterMSCKF` 类文档。

目标数据流：

```text
Camera + IMU
  -> feature tracking
  -> initialization
  -> IMU propagation
  -> visual update
  -> pose / velocity / covariance
  -> ROS odometry and TF
```

暂时跳过 EKF/MSCKF 推导、Jacobian、协方差块、FEJ、特征参数化、自标定、helper 内部、`ov_eval` 和仿真器。

完成标志：能解释传感器标定、时间同步、特征跟踪、初始化、传播、更新和输出的顺序，并理解 VIO 不是
相机即插即用地产生可靠位姿。

## 8. 阶段 6：无人机自治系统与规划

- 仓库：[`aerostack2/aerostack2`](https://github.com/aerostack2/aerostack2/tree/1.1.3)
- 版本：`1.1.3`；最新架构变化可补看 `main`。
- 定位：无人机自治系统分层主线。
- 许可证：BSD-3-Clause。

阅读顺序为 README、官方 Concepts、Aerial Platform 接口、Behavior Action 接口、`as2_msgs`、`as2_core`、
一条运动 behavior 接口、`as2_motion_reference_handlers`、`as2_motion_controller` 和
`as2_aerial_platforms`。

暂时跳过 behavior tree 内部、Python API、Gazebo 资源、多机任务、具体飞控适配、硬件驱动和控制器插件
细节。在线文档版本标题可能落后于 `1.1.3`，因此源码入口以固定 tag 为准。

完成标志：能解释“任务/应用 -> Behavior Action -> motion reference -> controller -> actuator command ->
aerial platform”的分层，并知道学习它不等于照搬整个框架。

### 8.2 GCOPTER

- 仓库：[`ZJU-FAST-Lab/GCOPTER`](https://github.com/ZJU-FAST-Lab/GCOPTER)
- 版本：`main`，阅读时记录 commit；旧 `v0.0` 不作为稳定版本。
- 定位：高级选读，理解轨迹优化结构。
- 许可证：MIT。

阅读顺序为 README 的问题定义、论文中的安全走廊/动力学/轨迹表示概念、`global_planning.cpp` 编排、
`trajectory.hpp`、`sfc_gen.hpp`、`minco.hpp`，最后才是 `gcopter.hpp`。

暂时跳过优化器、几何算法、求根器、体素地图和公式实现。其示例为 ROS 1/Catkin，维护节奏较慢，不是
ROS 2/Humble 教材。

完成标志：能解释“路径/自由空间 -> 安全飞行走廊 -> 带动力学约束的平滑轨迹”。

### 8.3 EGO-Planner-Swarm

先读默认 README 的问题定义和论文，再读 `ros2_version` README、`plan_env`、`path_searching`、

完成标志：能分清环境表示、路径搜索、B-spline 优化、重规划状态机、轨迹输出和多机通信的职责。

## 9. 阶段 7：回到项目接手
